# 停電時のカクつき調査

対象: dev の 82bc7af。調査ブランチ: td-dev-blackout。
以下の原因調査は変更前の記録。続く実装結果を同ブランチに追加した。

## 実装結果

- 既存の「影」設定を使用。オン時はFog・PointLight・敵補助光の構成を固定し、
  停電／復旧／暗視では値だけを変える。設定そのものの切替は構成変更を伴う。
- オフ時はFogなし・近距離PointLightなし。環境光と強めのキャッシュ済み暗幕で簡略表示する。
- 停電中は太陽光0、影マップの自動更新停止。復旧／暗視時に更新を再開する。
- 停電中の描画farを200にし、完全に隠れる敵を非表示・姿勢更新1000ms間隔にする。
  近づいた時・暗視時は表示と姿勢を即時復元する。身体の一部が境界に掛かる場合は残す。
- FPS暗幕のグラデーションをサイズ・描画設定が変わるまで再利用する。

同じ合成条件でオン時の停電は可視Meshが3148→12、オフ時は3148→404。
通常／復旧／暗視で3148へ戻る。停電前後で光源数とFog有無は各設定内で一致する。
これはシーン構造の確認であり、実際のGPU draw callやFPS改善率ではない。
通常時にもオン設定ではPointLight／Fogの演算が残るため、実機の通常FPSへの影響は未計測。
停電初登場の材質・武器や、設定自体の切替によるコンパイルは残り得る。
簡略表示の遠方切断と太陽光0による見た目も実機での確認事項。

確認済み: lab3d-models、enemy-animation、aim-cache、blackout-overlay、
graphics-settings、menu-ui の各Nodeテスト。実ブラウザー／GPU計測は未実施。

## 結論と確度

最有力は、停電の切り替えによる描画プログラムの切り替えと、暗くなっても減らないモデル・影の処理。
コードと構造比較で以下を確認した。ただし実ブラウザーのGPUプロファイルは未取得で、
発生環境での主因やフレーム時間の寄与率はまだ確定していない。

### 1. 切り替え時にシェーダーの条件が変わる（初回停止の有力候補）

client/lab3d.js:681付近で、通常時は scene.fog=null、停電時は Fog を設定する。
同時に enemyFill.visible=false、nearbyLight.visible=true へ切り替える。
通常時の主シーンは DirectionalLight 2 / PointLight 0、停電時は 1 / 1 になる。
ドローン操縦・暗視でも通常時の構成に戻る。

同梱の Three.js r149（client/vendor/three.min.js）の getParameters / getProgramCacheKey は
Fogの有無と光源数をシェーダー条件・キャッシュキーへ含める。
描画対象収集の Dt は不可視ノードを除外するため、この visible の変更は実際に光源数を変える。
USE_FOG はプリプロセッサ条件であり、色・強度のuniform変更だけではない。
既存プログラムがなければ停電用のプログラム生成・GPUコンパイル／リンクが必要になる。
材質インスタンスの数が、そのままプログラム数になるわけではない。

初回だけ強く止まり、同じモデル構成での2回目が軽くなるなら、この仮説を強く支持する。
停電中に初登場するモデル・武器・効果には別の未生成バリアントがあり得る。

### 2. Fogは遠方モデルの処理を止めない（停電中の負荷を減らせていない）

camera.far は5000のまま、停電Fogは視点奥行48〜160。
敵の生成・座標・歩行更新は従来の一覧を通り、遠方のモデルをFog距離で非表示にはしない。
Three.jsの通常の錐台判定は存在するが、Fog距離はその打ち切り条件に使われない。
fog_fragment は最終色を黒へ混ぜる処理で、遠方だからといって描画前に除外しない。
したがって見える範囲が狭まっても、モデル更新・描画候補が減る保証はない。
これは通常時からある負荷の継続であり、単独で「停電時だけ急増」の証明ではない。

### 3. 暗い太陽光の影を更新し続ける（削減余地）

停電中も sun.castShadow=true、影設定がONなら renderer.shadowMap.enabled=true。
太陽光の強度を1から0.08に落としても、影マップ1024×1024の更新は止めていない。
nearbyLightにはcastShadowを設定しておらず、PointLightの6面影が追加される構成ではない。
この項目も主に既存負荷の削減余地であり、停電による影パス数増加は確認していない。

### 4. 全画面Canvas暗幕の追加（優先度は低め）

FPSのapp.js:2689付近で、停電中は毎フレームRadialGradientを作り全画面を塗る。
高解像度では追加の描画・合成負荷になる可能性がある。
2D経路のdrawBlackoutSignalsやdrawBlackoutEnemyGlowは、FPSの早期return後には実行されない。
FPSの問題をこれらのループへ帰属させる根拠はない。

## 構造比較

実行: `node tools/inspect-blackout.cjs`

実マップの非壁セルを全て可視床候補とし、GRUNT64体、同じ視点・同じ個体・同じ材質で比較。
WebGLRendererはスタブ。以下はシーン構造の数で、GPU draw call・フレーム時間ではない。

| 条件 | Fog | Directional / Point | 影光源 | 可視属性を持つMesh | castShadow Mesh |
| --- | --- | --- | --- | --- | --- |
| 通常 | なし | 2 / 0 | 1 | 3148 | 3143 |
| 停電初回 | あり | 1 / 1 | 1 | 3148 | 3143 |
| 停電次フレーム | あり | 1 / 1 | 1 | 3148 | 3143 |
| 復旧 | なし | 2 / 0 | 1 | 3148 | 3143 |

全条件で材質インスタンスは18。

この数には錐台外の物体も含むため、3136回の無駄な描画を意味しない。
実マップの開放状態・敵配置を再現した測定ではなく、距離除外の有無を検証する合成条件である。

既存確認: `node client/tests/lab3d-models.cjs` 成功。
照明・Fog・暗視・復旧の動作を確認するテストだが、描画器スタブのためコンパイル停止やGPU速度は検出できない。

## 改善案（優先順）

1. **停電時のシェーダー生成を避ける。**
   最小の見た目変更で済む案は、ロード／準備中に通常・停電の構成を事前compileすること。
   主シーンの敵タイプ・地形・施設・効果の材質／Instancing等の条件を揃える必要がある。
   現在画面内の材質だけの事前処理では、後から登場するモデルを網羅できない。
   別案としてFogを常設し通常時はカメラ範囲外のnear/farに置く、光源のvisibleを固定して
   intensityを0へ切り替えることで条件を固定する。こちらは通常時にもFog／PointLightの計算が
   残り得るため、通常時のGPU時間と見た目を比較して採否を決める。

2. **停電の可視距離に合わせて描画・姿勢更新を減らす。**
   Fogで完全に隠れる敵等を、半径・高さと余裕幅を持たせて描画対象から除外する。
   状態・戦闘・通信は維持し、表示へ戻る時は現在姿勢を即時反映する。
   スナイパーの現在の全更新例外、HS／死亡演出、影の近距離への落ち込み、暗視への即時復帰を確認する。
   camera.farだけの短縮ではCPUの姿勢更新は減らず、大きなInstancedMeshの地形も一括では除外できない。
   単純な距離160での切断は境界の欠けを起こすため避ける。

3. **停電中の影マップ更新を抑える。**
   低強度の太陽光による影が必要か見た目を比較する。必要性が低ければ更新停止／低頻度化を検討する。
   shadowMap.enabledやcastShadowの単純切り替えは別のシェーダー条件変更を起こし得る。
   構成を保ったautoUpdate／needsUpdate制御も候補とし、視点移動や復旧時の古い影を検証する。

4. **FPS暗幕をキャッシュする。**
   FPS経路のグラデーションは形が固定なので、解像度変更時だけ作る画像を再利用する案を比較する。
   全画面の合成自体は残るため、描画器対策より先に大きな効果を期待しない。

## 実機での切り分け手順

- Goldを持つデバッグ状態で、同じ敵数・武器・視点・解像度を保って通常→停電→復旧を2回記録する。
  敵やラウンド開始が同時に増える条件を分ける。変更前コードのデバッグ開始額は今回変更していない。
- 初回切替前後のフレーム時間、WebGLのプログラム生成／リンク、プログラム数を記録する。
  継続負荷は停電前後それぞれ数秒の中央値・p95・最大値で比較する。
- GPU時間／主スレッド時間、主シーン＋手元の合計draw callと三角形数、影パスを確認する。
  二度renderするため、renderer.infoの自動resetで手元だけを計測しないようにする。
- 停電中に影更新だけ止める、暗幕だけ止める、遠方表示だけ止める試行を個別に比較する。
  暗視・ドローン・スナイパー・復旧と画面境界を含めて画質と動作を確認する。
- 初回だけ突出するなら案1、継続的に重いなら案2・3を優先する。

## サーバー側

GameSession.startBlackoutは解放済みブレーカーから1〜2個を選ぶ。
SnapshotBuilderは既存の停電フラグ／ブレーカー一覧を送る。
敵による停電も同じblackoutActiveにまとめるため描画の切り替えに到達する。
CPUのブレーカー復旧行動には停電時の分岐があるためサーバー負荷を完全には否定しないが、
今回の読解では停電開始時に全地形を再生成するような処理は見つからない。
