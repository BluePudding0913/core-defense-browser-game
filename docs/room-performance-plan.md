# 全ルームの処理待ちを減らす修正方針

調査日: 2026-10-06。調査基点: `46728b7`（dev）。今回は調査、測定用ツール、実装計画まで。ゲームの動作を変える修正は含めない。

## 確認した構造

| 箇所 | 現状 | 影響 |
| --- | --- | --- |
| `WasdServer.ticker / tickSafely` | 単一スレッドで全室を50msごとに順番に更新。全体を`gameLock`で囲む | 重い部屋が全室の更新と入力受付を待たせる。50msを超えると定期処理が遅れる |
| `onOpen / onMessage / onClose / handleMatch` | ゲーム状態、参加、予約操作も同じロック | プレイ中の負荷が参加・切断・マッチングにも波及 |
| `sendSnapshot` | 100msごとに状態JSONを生成。定期処理から呼ぶ場合、送信呼び出しまで外側のロックが残る | 状態生成、フレーム生成・キュー投入も全体の占有時間に加算 |
| `broadcastRoomLists / sendRoomList` | 500msごとに検索接続ごとに全室を並べ直し、JSON生成。接続・切断時にも配信 | 検索接続数×部屋数で仕事が増える。`joinable`はセッションの予約によって違うため、単純な共通JSON化は不可 |
| `GameSession.findPath` | BFSをキューが空になるまで続ける。到達可能なタイルのうち目標座標に最も近いものを選ぶ | 隣接目標でも探索範囲全体の判定と配列・キューの割り当てが発生 |
| `moveEnemyToward / nextBotWaypoint / spawnEnemy` | 遮蔽時の敵は概ね1秒ごと、CPUは0.65秒+slot×0.06または目標変更時に再探索。屋内出現時にも探索 | 個体ごとの経路は既に短期間再利用されるが、同じ目的地への探索結果を個体間で共有していない |

マップは2080×2080、タイル40、探索配列は52×52=2704要素。敵の探索は半径17でマップと解放区域を確認し、防衛設備を迂回しない。CPUは半径5でblock/barricadeも迂回する。実際の敵の移動時には設備との衝突判定がある。この差を最適化で勝手に変えない。

Java-WebSocket 1.6.0のローカル依存JARを逆アセンブルして確認したところ、`send(String)`はフレームを生成して`outQueue`へ追加する。キューは容量指定なしの`LinkedBlockingQueue`。ネットワーク送信完了まで同期的に待つ構造ではない。遅い接続に対する主な懸念は、未送信データの蓄積、古い状態の遅延配信、メモリとGC負荷。アプリ側の`sendIfOpen`には滞留量・滞留時間による制御がない。

`tickSafely`の例外処理は全室のループの外側にある。ある部屋で例外が出ると、その周期では以降の部屋の更新も飛ばされる。

## 簡易測定と限界

Windowsの専用worktree、Java 23.0.1、既存コードで実施。各条件100回ウォームアップ、200標本、同一JVM。反射呼び出し・結果サイズ読み出しの時間を含む。

| 条件 | 中央値 | p95 | 最大 |
| --- | ---: | ---: | ---: |
| 未解放、隣接床への経路1回 | 0.140ms | 0.263ms | 4.513ms |
| 未解放、隣接床への経路100回を連続実行 | 14.223ms | 26.407ms | 42.776ms |
| 全区域解放、隣接床への経路1回 | 0.287ms | 0.590ms | 1.207ms |
| 全区域解放、隣接床への経路100回を連続実行 | 21.734ms | 35.739ms | 43.541ms |
| 全区域解放、敵0のロビー状態JSON生成 | 0.211ms | 0.398ms | 1.562ms |

最後のJSONは9671文字。未解放の探索座標は(420,100)→(460,100)、全解放は(100,100)→(140,100)。探索対象は半径17、防衛設備迂回なし。

100回は探索集中時のコストを見る人工条件であり、100体の敵が毎周期この探索をするという意味ではない。状態生成の測定も通信・敵多数・全室更新を含まない。実運用の収容部屋数や通信負荷は、この数字から断定できない。

再現手順（専用worktreeの`server`内）:

```powershell
.\mvnw.cmd -o test
.\tools\run-pathfinding-probe.ps1
```

必要な依存が未取得なら初回は`-o`を外す。ツールはテスト結果XMLのJavaとクラスパスを使い、生成物を`target/performance-probe`に置く。サーバーや外部接続は開始しない。既存のサーバーテスト162件は全件成功。

## 段階的な実装

### 1. 処理時間を分けて計測する

まず動作を変えずに、周期の予定時刻からの遅れ、実行時間、ロック待ち時間と保持時間、部屋別のupdate・状態生成・送信キュー投入時間を計測する。探索回数・訪問数・時間、JSONのUTF-8バイト数、接続ごとの送信滞留量・継続時間も記録する。毎周期ログを吐かず、集計して出力する。部屋別値は上位の重い部屋などに絞り、集計自体の負荷とメモリも制限する。

部屋数1/4/16/64、敵数0/50/200/500を基本に、実際のR40/R50相当の小型敵同時出現も試す。人間4人と人間1人+CPU3人、解放区域、設備数、コア移動、検索接続数を変える。全組合せを闇雲に実行せず、単室から段階的に増やす。通常の部屋と高負荷の部屋を同時に動かし、通常部屋の入力受信→状態へのackInput反映と周期遅延を比較する。

受け入れ基準は対象の運用機材・目標同時部屋数を明記した上で設定する。初期目標は通常負荷で周期実行時間p95が50ms未満、遅延の累積がないこと。p99、50ms超過率、入力反映時間も見る。CPU使用率・ヒープ・GCを併記し、平均値だけで判定しない。

### 2. 経路探索の余分な仕事を減らす

最初の動作修正は`findPath`の早期終了と、マップの通行可否判定の再利用。現在は「目標のタイルに到達」ではなく「実座標から最も近い到達可能なタイル中心」を選ぶため、単純に目標タイルで打ち切ると経路が変わる場合がある。タイル中心の到達可能目標では到達時に終了する。非中心・壁内・未解放・到達不能目標では、当初は既存の最寄り到達点へのフォールバックを維持する。さらに最寄り候補を事前に定める最適化は別段階にする。

探索用配列・キューは部屋専用として再利用し、訪問世代によって毎回の全初期化を減らす。通行可否マスクは半径と区域解放状態ごとに作り直し、CPU向けは設備配置・撤去・破壊・運搬も反映する。共有するのは探索結果で、敵やCPUの経路進行位置は個別に保持する。

回帰確認: 近距離・同一位置・壁内・到達不能目標、区域解放前後、半径差、設備迂回、屋内出現、コア移動、最短距離と同距離時の選択。変更前後の訪問数と時間も比較する。

### 3. 共通目的地への経路を部屋内で共有する

コアなど共通目的地へは逆向きBFSの経路木を部屋内で共有する候補を優先する。開始地点が違っても再利用できる。同じ出現地点の出現時経路も再利用する。敵1体ごとの探索から、目的地と通行条件ごとの探索へ減らす。

キャッシュキーは目標セル、半径、設備迂回有無、地形世代を含める。目標の実座標に依存する最寄り点の選択は、実座標をキーに含めるかフォールバック対象として切り離す。コアの移動と区域解放で失効させ、CPU向けには設備世代も加える。リセット時もクリアする。動くプレイヤーへの追跡はキャッシュ上限・期限を決め、まず個別探索を維持する。複数ルームの状態依存キャッシュは共有しない。

探索頻度の分散は追加策とする。同時出現した敵の1秒タイマーが集中するケースを測り、必要なら再探索時刻をずらす。経路上のルート目標、wanderの微小変位、コア移動により共通化率が下がるため、ヒット率を測って適用対象を決める。

### 4. 送信待ちを制限し、送信を状態ロックの外へ出す

状態JSONと送信対象は部屋の状態が一貫している間に確定し、不変の送信データとして渡す。`GameEventSink`も直接送信せず、部屋のイベントを蓄える。送信は別の上限付き処理系で行い、接続単位の順序を維持する。参加時のmap→welcome→初期状態の順序を保証する。

状態更新は接続ごとに未投入の最新1件を保持して古い状態を置換する。ライブラリのキューへ既に投入したフレームは消せないので、滞留中は新しい状態の投入を抑制する。`hasBufferedData`だけでは滞留バイト数や時間を判断できないため、1.6.0で使える測定方法を確認し、アプリ側とライブラリ側の両方の蓄積を監視する。

map/welcome/操作応答など必須メッセージは順序を保つ。演出など破棄可能なイベントは別に扱う。全イベントを無制限に蓄えない。設定した容量・滞留時間を超えた接続は切断し、再接続後に最新状態で復帰させる。状態省略中も入力確認番号が次の最新状態で反映されることを確認する。

確認: 読み取りを止めた接続を含む継続負荷でメモリが増え続けず、通常接続の更新が続くこと。滞留解消時に古い状態を大量再生しないこと。切断競合と再接続、必須メッセージ順序も試す。しきい値は測定して設定する。

### 5. 部屋単位に処理とロックを分ける

共通ロックは部屋登録・削除・最大部屋数・重複合言葉などの管理に限定し、各GameRoomに専用ロックを設ける。部屋のGameSession、予約、所有者、接続割当の整合性はその部屋で守る。部屋一覧は各部屋が公開する不変の要約を読む。予約を考慮する`joinable`は閲覧セッション別に計算するが、表示生成中に予約を変更しない。期限切れ予約の掃除は部屋の処理へ移す。

ロックを分けるだけでは単一ticker上の順番待ちは残るため、更新も上限付きワーカープールへ分離する。各部屋は同時に1更新まで、待機タスクも1件までとし、遅い部屋のタスクを積み上げない。ワーカー数はCPU数と測定結果から決め、部屋数分の無制限スレッドは作らない。1部屋の例外はその部屋で捕捉する。

固定dt=0.05の扱いを決めてから実装する。遅延時に無制限の追いつき更新や巨大dtを入れず、追いつき回数を制限し、遅れを計測する。ゲーム時間が遅くなる許容範囲も明示する。共有CPUが飽和すれば処理分離後も他室への影響は残るため、上限部屋数と負荷時の方針を測定結果で調整する。

部屋管理ロックと部屋ロックは原則同時に持たない。候補部屋取得後に部屋の有効性・空席を再確認し、定員・予約・閉鎖状態を同じ部屋の排他区間で確定する。削除済み部屋への遅延タスク、旧接続からの入力、再接続時のclose、所有者移譲、予約満了、空室削除を確認する。サーバー停止時にticker・ワーカー・送信処理を停止する経路も用意する。

## 実施順と完了条件

計測 → 単発探索の最適化 → 共有経路 → 送信制御 → 部屋分離を、独立した変更として確認・コミットする。計測で送信滞留が先に問題になる場合は送信制御を前倒しする。状態JSONの固定ルール部分や部屋一覧の生成共有は、生成時間の寄与が大きい場合に追加する。

最終確認は、通常部屋+重い部屋+読み取り停止接続の同時実行。通常部屋の周期と入力反映が改善し、キュー・ヒープに上限があり、予約・再接続・ゲーム進行の既存機能が通ること。Javaの全テストに加え、`client/tests/rooms-server.cjs`の実サーバー接続テストを使う。性能判定は同じ機材・条件・ウォームアップで変更前後を比べる。

まだ未実施: 全室の実通信負荷測定、処理区間別の計測、遅い接続の継続測定、ゲーム動作を変える実装修正。今回の簡易測定は経路探索の優先調査を裏付けるもので、全体のボトルネック順位を確定するものではない。
