# 軽量化調査（2026-10-15）

対象: dev の `18cce5f`。調査ブランチ: `td-dev-perf-audit`。
ゲームの実装は変更せず、コード確認・既存の構造検査・合成CPU計測を行った。
ブラウザーのPerformance記録、GPU時間、実プレイ中の通信量・サーバー時間は未取得。
以下の優先度は実装構造と合成計測に基づき、実環境の主因を確定するものではない。

## 結論

最初の候補は、HPバー・名前・施設ラベルを表示するための地形遮蔽レイ。
次に、通常時の敵モデルのMesh・影、全状態配信の固定部分を検討する。
既存の射撃索引や敵アニメーション間引きを再実装する必要はない。

| 優先度 | 対象 | 確認した負荷 | 対策の方向 |
| --- | --- | --- | --- |
| 1 | クライアントの表示用遮蔽判定 | 表示候補ごとに地形のInstancedMeshへレイ | 地形の空間分割・ブロック索引、同一フレーム内の結果共有 |
| 2 | 通常時の敵モデル・影 | GRUNT64体の合成シーンで可視Mesh3,148個 | 同じ関節・材質の形状結合、遠方LODと影の簡略化 |
| 3 | 状態配信 | 武器定義等も含め全状態を10Hzで再生成・配信 | 固定定義の別配信、次段階で変更分配信 |
| 4 | サーバーの設備索敵 | 設備ごとに敵全件を検索 | 近傍候補検索を追加、既存の選択順・判定を維持 |
| 5 | HUD・所持品 | 10Hzで表示更新、閉じた所持品も更新 | 値の変更時だけDOM更新、閉じたパネルは開く時に反映 |

## 1. 表示用遮蔽レイ

- `client/app.js:2656` のtext/barから `Lab3D.project` を呼ぶ。
- 傷ついた敵のHPバー、味方の名前とHPバー、設備、CORE、施設などが対象。
- `client/lab3d.js:433` のprojectは画面範囲判定後、`raycaster.intersectObject(terrain,true)` で遮蔽を調べる。
- 地形は `client/lab3d.js:77` で床・壁・天井等を5つのInstancedMeshへまとめている。
  描画のバッチ化はされているが、表示用レイの空間索引にはなっていない。
- 同じ味方やCOREでも、名前とHPバーは高さが違い、別々に判定する。
  同一座標・高さだけのキャッシュでは全ての重複を解消できない。

追加した `tools/inspect-projection-performance.cjs` は、全非壁セルを解放、
傷ついたGRUNT64体、固定カメラ、WebGLRendererスタブの条件でprojectを64回呼ぶ。
20回ウォームアップ後、7回の中央値を採用。

2026-10-15の実行例:

| 項目 | 結果 |
| --- | ---: |
| 地形インスタンス | 3,106 |
| 64回のproject中の地形Mesh.raycast呼び出し | 320 |
| 呼ばれた地形Meshのcountの累計 | 198,784 |
| 64回のprojectのCPU時間中央値 | 49.31ms |

countの累計はレイキャストへ渡したインスタンス候補の規模であり、
命中数・三角形交差数・GPU draw call数ではない。
全エリア開放の合成条件で、実際の開放状態や敵位置、端末性能で結果は変わる。
実ゲームのフレーム全体時間やFPSへの換算はできない。

対策は地形を部屋・チャンクごとに分けて候補を絞るか、
BlockTerrainの3Dブロックを使った専用の表示用遮蔽検索を用意する。
既存の高さ・天井・未解放区画・隣室解放時の壁の扱いを保つ。
照準用aimPointにも地形レイはあるが、同一フレーム内キャッシュは実装済み。
表示用レイと照準結果を混同せず、改修時は両者の互換性を検証する。

## 2. 敵のMeshと影

`node tools/inspect-blackout.cjs` の通常時は可視属性を持つMesh3,148個、
castShadow属性を持つMesh3,143個。GRUNT64体の身体に相当するMeshは3,136個（49個/体）。
これはシーングラフの数で、錐台カリング後の実draw call数ではない。

`client/lab-enemy-models.js` は形状・材質を共有し、個体ごとにノードを複製する。
共有によってGPU資源の重複は減るが、Meshノードと個別描画は残る。
姿勢の組み立ては間引いている一方、通常時の身体Mesh数や影は同じまま。
`client/lab3d.js:814` はシーン行列も明示更新する。

最初は同じ関節に固定された同じ材質の部品をまとめるのが候補。
遠方モデルの細部・影を減らすLODは見た目との調整が必要。
敵全体のInstancedMesh化は関節・個別被弾色・凍結・死亡フェードとの整合が必要で、
小さな改修としては扱わない。姿勢間引きのスナイパー例外も維持する。

## 3. 全状態配信

`GameConfig.java:9` は更新20Hz、状態配信10Hz。
`WasdServer.java:258` は単一tickerとgameLock内で各部屋の更新・状態生成・送信呼び出しを行う。
`SnapshotBuilder.java:72` 以降で毎回rules・areas・players・enemies・設備・資源等を構築する。
rules内には武器定義・レシピ等の固定情報と、CORE強化費用等の状態依存情報が混在する。
クライアントは受信ごとにJSON.parseし、状態を入れ替える。

まず固定定義を初回・定義変更時だけ配信し、動的価格等は定期配信に残す。
接続復帰・サーバー再起動・初回状態受信の順序を保証する。
敵のtype/maxHp等の初期情報と座標等を分ける差分配信は次段階。
削除・巻き戻し・再接続の全量同期が必要となるため、一度に導入しない。
現状もスナップショット生成は部屋ごとに1回で、接続人数ごとの再生成ではない。
無人部屋は状態送信を省くが、復帰仕様に従ってゲーム更新は続く。

## 4. 設備の索敵

`GameSession.java:1671` のupdateDefensesは、有刺鉄線・地雷・発射可能タレットごとに
全敵を検索する。タレットは射程内の敵に見通し判定を行い、COREに近い敵を選ぶ。
設備D個・敵E体で検索が概ねD×Eへ増える。
既存EnemySpatialIndexは射線候補用であり、この近傍検索には使われていない。

近傍・範囲検索APIを追加する候補。ただし索引維持コストもあるため、小集団では全件を維持する。
同距離の対象選択、地雷の発火順、速度低下・範囲ダメージの対象を従来と比較する。
CPUにも敵全件検索があるが、計測前に全検索を一括置換しない。

## 5. DOMと解像度

receiveState → updateHudは10Hzで動き、`app.js:1024` の味方欄と
`app.js:1040` の能力欄はinnerHTMLを再設定する。
`app.js:1076` は閉じた所持品にもupdateInventoryを呼ぶ。
所持品ボタン自体は既に再利用しているため、全面作り直しと誤認しない。
DOMノード再利用・値比較・非表示パネルの遅延更新が小規模な改善候補。

`app.js:1904` はDPR最大2、lab3dは同じCanvas寸法で描画する。
DPR2はDPR1に比べ画素数4倍。GPU時間が支配的なら3Dの描画倍率設定は候補だが、
文字を含む2D HUDの解像度とは分け、鮮明さを維持する。
表示用レイやサーバー負荷は描画倍率だけでは解消しない。

## 既に対策済み

- 射撃候補: 64体以下は全件、65体以上は80×80の空間索引。
- 敵姿勢: 画面外250ms、遠方100ms、停電の非表示対象1000ms。スナイパー例外あり。
- 停電: 光源・Fog構成の維持、影更新停止、far200、遠方の敵非表示、暗幕Gradient再利用。
- 地形: InstancedMesh化、マップ・解放範囲が変わるまで構築を再利用。
- 移動: EnemyNavigationのCORE距離場共有、同一タイルなら再計算を省く。
- 照準: 同一描画フレーム内の結果共有。
