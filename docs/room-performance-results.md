# 部屋ごとの負荷分離: 実装と確認結果

2026-10-06。比較基点は`eb167df`。変更はゲームの20Hz更新と10Hz状態通知を維持しながら、経路探索、送信待ち、部屋間の処理待ちを減らすもの。

## 実装したこと

- 処理時間は固定長256標本に記録。p95/p99は直近256回、最大値・件数・50ms超過件数は累積。探索訪問数、再利用回数、状態JSONのUTF-8バイト数、更新見送り数、送信の滞留量・時間、切断と部屋更新失敗も記録する。
- 部屋内で通行マスク4件、経路128件、目的地からの逆BFS経路木8件まで保持。配列と探索キューを再利用する。区域解放状態とblock/barricade配置を実際の状態と照合して失効させ、再開始時にもクリアする。コア移動・目標の実座標はキーに反映する。
- 目標がタイルの内側にあり、その中心が一意の最寄り点なら、中心に到達した時点で探索を終了できる。目標の壁内・到達不能・タイル境界での同距離候補は従来の最寄り到達点への探索を維持する。共有経路木は最短距離を保つが、同じ長さの経路が複数ある場合に選ぶ道は変わりうる。
- 敵の半径17・設備迂回なし、CPUの半径5・設備迂回ありという通行条件を維持。経路自体は不変、進行位置は個体別。敵のwanderによる小さな目標のずれも、一意の最寄り点が同じなら経路木を共有できる。
- 接続ごとの送信待ちは128件・512KiBまで。未送信の状態/部屋一覧は最新1件へ置換し、容量不足の演出は省略する。必須メッセージが上限を超えるか、ライブラリの送信待ちが5秒以上連続した場合、その接続だけを4001で切断する。送信ワーカーは2本、待機タスクは256件まで。ゲームロック内ではキューへ追加するだけで、フレーム生成と実送信は別処理にする。
- map→welcome→初期状態の投入順序を部屋のロックで保証。遅延中の状態を省略しても、次の状態に最新のackInputが入る。すでに通信ライブラリやOSへ渡したフレームは撤回しない。
- 各部屋に専用ロックと、同時1件までの更新タスクを設ける。更新ワーカーは既定でCPU数に応じて2〜4本、待機列は最大部屋数まで。遅い部屋の更新を無制限に積まず、終了待ちの周期は見送る。その間、その部屋のゲーム時間は遅くなる。大きいdtや無制限の追いつき更新は入れない。
- 部屋一覧は不変の要約を読み、ゲームのロックを待たない。予約を考慮する空席情報は閲覧セッション別に計算する。部屋登録と合言葉の重複確認だけは短い管理ロックを使う。クイックマッチ作成直前の再確認で部屋ロックを取得する際はtryLockを使い、管理ロック内で部屋を待たない。
- 更新例外は部屋ごとに捕捉し、ログは各部屋1秒に1回まで。停止時には定期処理・更新ワーカー・送信ワーカーを停止する。

## 実通信測定

Windows、Java 23.0.1、利用可能CPU 8、JVM上限512MiB、更新ワーカー4本。同一PC内の実WebSocket接続を使う。制御室1室はロビー、他の部屋に各200体の敵を配置。4人相当の人間状態（CPUなし）、全区域解放、設備なし、敵の速度とダメージを0にして負荷を継続させる。1接続/部屋から50ms待機を挟んで連番付き入力を送る（実間隔はOSのタイマー精度にも依存する）。最終部屋には受信バッファ1024バイトで、読み取りを一切しない接続も追加する。修正後は滞留切断後、当該1枠が従来仕様でCPUに切り替わる。

接続完了後2秒待ち、8秒間を測定。入力反映時間は送信からstateのackInputで確認されるまで。状態間隔は制御室が受信したstateの間隔。乱数によるwanderは継続するため、各試行は完全に同一の軌跡ではない。

| 条件 | 入力反映p95 | 入力反映最大 | 状態間隔最大 |
| --- | ---: | ---: | ---: |
| 変更前: 4室、各高負荷室200体 | 145.539ms | 196.687ms | 188.963ms |
| 処理分離後: 4室、各高負荷室200体（目標ずれの共有追加前） | 123.876ms | 126.606ms | 109.853ms |
| 変更前: 16室、各高負荷室200体 | 575.570ms | 648.018ms | 637.102ms |
| 最終経路最適化後: 16室、各高負荷室200体 | 108.804ms | 120.733ms | 132.173ms |
| 最終経路最適化後: 64室、各高負荷室200体 | 110.954ms | 124.903ms | 132.763ms |

16室では高負荷室1の1496回の探索要求のうち1484回が経路または経路木の再利用。探索時間p95は0.004ms、訪問数は累積10019。64室でも同じ高負荷室の1768要求中1756回が再利用だった。CPUなし・固定位置でのこの比率を、移動する敵やCPUの多い実試合へそのまま適用しない。

読み取り停止接続は修正後の4/16/64室でそれぞれ1件だけ切断された。64室の試行ではアプリ送信待ち最大68020バイト、通信ライブラリのキュー観測最大34675バイト、滞留最大約5.014秒。通常接続の受信は継続した。

64室で保持ヒープは待機後約39.6MB、測定終了後約106.3MB（いずれも明示GC後）。キャッシュ等の形成も含む短時間の差分で、長期的なメモリ安定性を証明する値ではない。キャッシュ・アプリ送信待ち・ワーカー待ち件数にはコード上の上限を設け、回帰テストでも送信容量と更新待ちの上限を確認した。

この測定はサーバーとクライアントを同じJVMで動かし、クライアント側JSON解析も同じ機材の負荷に含む。実際の通信環境、移動・射撃・CPU行動・設備変更・連続ラウンドを再現した収容人数の保証ではない。状態送信が10Hzなので、入力反映のp95が約100msでも想定範囲であり、50ms周期の実行時間とは別指標。

## 回帰確認と再現

最新dev取り込み後のJavaテスト174件成功。経路の到達点と最短長、設備/区域変更、部屋停止中の別室入力・更新・一覧、同室の待機タスク抑制、部屋例外後の別室更新、送信の容量上限・状態置換・必須メッセージ順序・滞留切断を追加で確認した。実サーバーのクライアントテストでは参加、予約満員、非公開部屋、所有者移譲、再接続、最後の退出、合言葉再利用が成功した。

専用worktreeのserverで:

```powershell
.\mvnw.cmd -o package
.\tools\run-pathfinding-probe.ps1
.\tools\run-room-load-probe.ps1 -Rooms 16 -Enemies 200 -Seconds 8 -BaselineRef eb167df
.\tools\run-room-load-probe.ps1 -Rooms 16 -Enemies 200 -Seconds 8
```

基点指定時は過去のJavaソースとマップをignoredのtarget内に取得してコンパイルし、チェックアウトを変更しない。依存バージョンは現在のクラスパスを使うため、大きく異なる古い基点との比較には対応しない。制御室以外の敵数と部屋数を変えられる。Rooms=1の場合は制御室も高負荷室となる。この環境ではJavaの乱数初期化に時間がかかる場合があり、通信開始に最大30秒待つ。

ルートで、JAVA_HOMEをJDKへ設定して:

```powershell
node client/tests/rooms-server.cjs
```

## 運用設定と残る制約

- `CORE_PERF_LOG_SECONDS=30`等を指定すると、サーバー集計と更新最大時間が長い上位3室の集計を表示する。既定0では表示しない。時間の単位はms。
- `CORE_ROOM_WORKERS`で更新並列数を変更できる。既定2〜4本。部屋数を増やす際はCPU・GC・周期見送り・入力反映を合わせて確認する。
- 同じ部屋の入力と更新は引き続き排他的。計算負荷全体がCPUを使い切る場合や検索接続が大量にある場合は、部屋を分離しても共通の機材と定期処理の影響が残る。
- 送信待ちの512KiB/128件と5秒は今回の初期値。低速環境でも正常な接続がこの条件に達する場合は切断される。最後の人間接続の切断で部屋を削除する従来の仕様は維持しているため、その場合は同じ部屋への復帰はできない。
- 長時間の実試合、CPUあり、設備数の多いケース、R40/R50の連続負荷、WANでの帯域制限は、対象の運用環境で追加測定する。今回の短時間測定だけで最大64室を運用保証するものではない。
